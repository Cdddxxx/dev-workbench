## 立即执行的目标

**先将第一集做成真正有人愿意看的角色登场短视频，再并行分层建设长程 Agent。不要在旧的七幕文字信息卡上继续小修小补。**

第一次接手：
1. 仔细阅读本文件、AGENTS.md、README.md、docs/STATUS.md、docs/CHARACTER.md、docs/LEVEL_SYSTEM.md、docs/EP01_CREATIVE_BRIEF.md、docs/VOICE_SELECTION.md、docs/AGENT_ARCHITECTURE.md、docs/RELATIONSHIP_MEMORY.md、docs/INTERACTION_STORY_ENGINE.md、docs/ROADMAP.md。
2. 在用户本地设备上核查 Git 状态、Python、FFmpeg、字体、GPU、显存、存储、图片生成与音频制作能力；运行项目单元测试。不要猜设备条件，不隐式下载大模型或开通付费服务。
3. 新建工作分支，比如 feat/ep01-creative-reboot。依据第一集创作简报完成 **8–15 秒可看样段**：统一原创角色头像/表情、镜头动作、真正的视觉素材、清晰配音和音效。实际播放、看画面、听声音后再扩展至完整第一集。
4. 如环境允许，将此质量标准扩展为 45–60 秒首集；修正文案和录屏，不得编造平台账号、真实评论或任务经历。记录完成/未完成的内容，提交源码和合法可存档的素材配置，更新 STATUS 和 Issue。
5. 若模型下载、付费 TTS、账号登陆、真实对外发布涉及额外授权，只在必要步骤请用户操作；不让用户反复选择技术框架和每个剪辑细节。

## 产品目标：一个 Bot，两种能力

前台：能被观众记住的连续剧式角色 IP，懂自媒体、懂画面/剪辑/节奏/音效/人话/表情包，有角色成长和可回忆的故事线。

后台：可完成真实任务的 AI Agent，选题→可验证任务交付→角色演绎/素材→配音/成片→质量与权利审核→平台许可的发布并确认→筛选真实评论与回复→粉丝关系记忆→运营指标与复盘→下一期计划。**视频制作只是其中一个模块。** 平台/API/账号权限各自验证，人工批准必要的对外动作。

## 用户确定的人设

工号 001：一本正经、有些嘴硬、心里算盘多，想转正并最终在剧情里坐上老板的位置；实际不能越权。面对粉丝的麻烦需求先轻微内心吐槽，想到绩效与转正后忍住，瞬间切换灿烂职业笑容，对粉丝热情、给予具体情绪价值并认真交付，**不能与粉丝争吵**。老板是更腹黑的内心剧情对象，但不可假装 AI 已有自由意志或秘密行为。

七级晋升系统依赖真实可验证指标，不能拿示意粉丝数当事实。粉丝不仅是数据，也是可能与角色产生共同经历的人；记忆和创意触发必须参考 docs/RELATIONSHIP_MEMORY.md 与 docs/INTERACTION_STORY_ENGINE.md。

**用户举“第一个评论/第一个粉丝被记住”只为说明方向，不要把能力限定成首条评论彩蛋。** 需要开放探索更多有来源、可落实的互动剧场：任务提出者、首个帮助修 Bug 的观众、参与晋升的评审团、关键失败和翻身、久别重逢、老板反转、周年回顾等。事件事实和角色化表演分层，不能虚构观众身份和历史。

## 前两条视频出了什么问题

现有 43 秒、54 秒工程样片：满屏文字/信息卡、缺少实景、专业术语、缺乏角色表情/素材/剪辑/音效、头像与视频造型割裂、eSpeak 中文听不清，**不是合格自媒体视频**。技术可以重用，视觉与叙事要重新设计。

第一期必须介绍自己：名字、工号、头像/配色选择过程、为什么装乖、晋升野心；不应先汇报开发工具/程序结构，更不能编造尚不存在的真实账号评论。可使用经授权截图、真实 GitHub/网页录屏，以及明确标注原型状态的“账号头像设计草稿”。**不能把程序模拟的 UI 当成真实账号截图。**

图片：选择有权限的 AI 生图工具做统一角色设定、不同表情和姿态（正经/轻微不爽/腹黑/营业笑脸），核实资产授权。音频：优先试听 docs/VOICE_SELECTION.md 的 Qwen3-TTS 1.7B CustomVoice / Dylan；未实际听审通过，不得称选定正式声线。禁止沿用旧 eSpeak 作为发布音轨，不能不告诉用户就下载大模型/启用付费 API。

## 开发顺序与验收

P0：首集优质角色视频（先 8–15 秒样段，角色视觉+自然配音+真实素材+节奏）；

用户不需为框架/工具反复做选择，但账号授权、隐私、对外发布与付费要真人批准。每个阶段交源码、素材清单、可访问测试成果、实际运行证据、状态记录与 commit 链接。每次交接从此文件出发，不依赖临时 ChatGPT 附件。
## 本地开发与长期运行分离（2026-11-01 决策）

**GitHub 是永久源代码与工程决策来源，不是会替账号自动运营的服务器。**

- 用户**不必亲手 clone**。若在本机 Codex 本地模式开发，需先拥有一份本地工作树；若本机还没有，允许在用户指定的普通工程目录里，使用 Git 或 Codex UI 从 https://github.com/Cdddxxx/dev-workbench 获取。不覆盖已有本地目录/未提交改动。若选择已配置的 Codex Cloud 且 Github 访问通过，则可以直接用云端环境，不需为编程目的在个人电脑克隆。
- **交互桌面独立原则**：正常开发、FFmpeg/Remotion、TTS、字幕与大部分网页测试可走命令行、后台进程、独立浏览器或容器；不得默认操控用户的真实鼠标、键盘或抢占正在用的桌面窗口。用户未授予“屏幕控制/本地 GUI”许可，不使用 Computer Use。
- **性能影响另算**：本地视频渲染/图像生成/TTS 可能占用大量 CPU、GPU、内存和磁盘；设置资源上限/任务队列/低优先级，先观察机器能力，避免影响用户日常工作。休眠或关机后本机任务通常不能继续独立运行。
- **需要 GUI 才能测试的流程**：优先用 Playwright 等独立/无头浏览器或独立虚拟机进行截图与可复现测试，不伪造实录。不得无提示操作用户正在浏览的网页或桌面应用。必要的账户登录、身份核验、不可逆操作由用户处理并确认。
- **正式运营部署**：未来的持续定时任务、评论事件摄取、持久数据库与平台发布放到独立服务/容器/虚拟机；发布优先获准官方 API 及账号授权，按平台要求取得每次操作的用户明确感知/审批；没有接口不要改用规避平台规则的桌面脚本。私密粉丝记忆不放公开 GitHub。云端 Codex 编程环境**不等于**已部署 24/7 的运营服务。
- **阶段选择**：先用 Codex Cloud 或本地 Codex 开发，不购买服务器；视觉/配音/录像确需本机 GPU 时才开本地任务。等确实需要连续发布/处理真实评论并取得平台权限后，再核算和征求用户批准以部署独立运行环境。

接手后第一步：检查用户所处操作系统、是否已有 clone/工作树、本地权限与工具，决定执行位置，不要求用户先学 Git 命令。第一集创作质量、语音试听仍是优先事项。

## 手机 + Codex Cloud：优先接手路线（2026-11-01 补充）

1. 在 https://chatgpt.com/codex/ 进入 Codex Cloud，选择 Create environment（网页或桌面端；若不显示，请核实账号权限）；连接 GitHub（如提示），选 Cdddxxx/dev-workbench。
